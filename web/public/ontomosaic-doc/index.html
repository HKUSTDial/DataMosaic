01 /WHY ONTOLOGY

Finding information is only half the task.

A retrieved row is not yet an understood fact. Definitions, qualifiers, and visual correspondences that determine an answer can sit on different pages and in different modalities.

01

Similar names. Different meanings.

Reported profit and core profit can share a year and unit while using different accounting definitions. Matching a label can select the wrong concept.

02

The qualifier is somewhere else.

The decisive detail may be in a legend, a formula, a footnote, or a separate definition. Finding a value can still miss what makes it meaningful.

03

The next question starts over.

Related questions often need the same definitions, source locations, and calculations. Without an explicit semantic layer, that work is rediscovered and reconstructed.

03 /CONSTRUCTION & EVOLUTION

Build from sources.
Improve from experience.

Two complementary paths: Build establishes initial semantics from questions and documents. Evolve uses task trajectories to reveal gaps, propose changes, and compare them against a frozen parent.

O₀

Source-driven Build

COLD START
  1. Questions & documents
  2. Semantic exploration
  3. Ontology draft
  4. Source audit & checks
  5. Initial ontology O₀

Check source support, definitions, and coverage. Build checks alone do not establish a gain in question-answering performance.

↓Start Evolve from O₀, or bootstrap from an empty baseline

Oₜ

Trajectory-driven Evolve

BOOTSTRAP / REFINE
  1. Freeze parent
  2. Execute & distill
  3. Construct & patch
  4. Audit & recheck
  5. Paired validation
  6. Publish or retain parent

Freeze the baseline before comparison. If a candidate is rejected, retain the parent, including when that parent is empty.

↳

Schema validity is not semantic correctness. Source review still needs to examine support, conflicts, and omissions. Conflicting knowledge can be merged, revised, kept separate, or left unresolved.
